# xiaohongshu-mcp 代码模块拆解（路线 B 底座评估）

> 仓库：`ref/xiaohongshu-mcp`（xpzouying/xiaohongshu-mcp，Go，Apache-2.0）
> 规模：77 个 `.go` 文件 / 约 13,948 行（含测试）
> 定位：一个 Go 程序同时是 **MCP Server + HTTP API + 小红书浏览器自动化引擎**。
> 底层：`go-rod`（Chromium DevTools 协议）+ 自研 `xpzouying/headless_browser`（打指纹补丁的内置 Chromium）。

---

## 一、分层架构总览

```
┌────────────────────────────────────────────────────────────────┐
│ L0 入口/装配   main.go · app_server.go · routes.go                │
├────────────────────────────────────────────────────────────────┤
│ L1 接口层      handlers_api.go (HTTP) · mcp_server.go+mcp_handlers.go (MCP) │
│               middleware.go · types.go                          │
├────────────────────────────────────────────────────────────────┤
│ L2 业务服务层  service.go (XiaohongshuService) · login_session.go │
├────────────────────────────────────────────────────────────────┤
│ L3 动作层      xiaohongshu/ 包（login/feeds/search/detail/      │
│  (真正干活)     comment/like/publish/notification/user_profile…） │
├────────────────────────────────────────────────────────────────┤
│ L4 浏览器层    browser/（工厂+二进制下载）· configs/ · cookies/   │
├────────────────────────────────────────────────────────────────┤
│ L5 拟人引擎    humanize/（延迟分布·贝塞尔鼠标·抖动点击·逐字输入）  │
├────────────────────────────────────────────────────────────────┤
│ L6 工具层      pkg/downloader · pkg/xhsutil · errors/            │
└────────────────────────────────────────────────────────────────┘
```

调用链：`HTTP/MCP → service.go → xiaohongshu 动作 → (browser + humanize) → 页面 DOM`

## 三、结论：路线 B 能白嫖什么

**✅ 开箱即用的（几乎不用改）：**
1. 登录态管理：cookie 持久化 + 指纹 seed 绑定，同号同指纹。
2. 全部原子动作：浏览 feed / 搜索 / 看详情 / 点赞 / 收藏 / 评论 / 回复 / 看通知。
3. 拟人引擎：对数正态延迟 + 贝塞尔鼠标 + 抖动点击 + 逐字输入 + 滚轮滑动。
4. 反检测底座：定制指纹 Chromium + seed 固定 + 代理透传。
5. 风控识别：captcha / login 重定向检测（现成的熔断信号）。

**❌ 完全没有的（这就是我们要写的"养号大脑"）：**

| 缺口 | 现状 | 我们要补的 |
|---|---|---|
| **无持久会话** | 每个动作独立开/关浏览器，服务无状态 | 一号一浏览器常驻，一个"会话期"(15–40min)内连续动作 |
| **无养号阶段** | 动作是"被调用才执行" | D1-2 只看→D3-5 点赞→第2周评论…的**阶段 FSM** |
| **无行为编排** | 只有单一原子动作 | "刷feed→点开→看正文→滑评论→偶发点赞→退出"的**概率动作序列** |
| **无配额/熔断** | 无 | 日配额 + 最小间隔 + 风险分 + 封控自动冷却 |
| **无多账号调度** | 一个 cookie 文件 = 一个号，一进程一号 | 账号池 / 设备池(profile) / IP池 + 调度器 |
| **默认无头** | `-headless` 默认 true | 养号改 **headful**（无头易被识别） |

## 四、建议新增的"养号引擎"结构（包在现有底座之上）

底层 `xiaohongshu`(动作) + `humanize`(拟人) + `browser`(反检测) **原样复用**，在其上新增策略层：

```
养号引擎（建议新增，独立于 MCP/HTTP 那套）
├── account      # 账号: 一号一 cookie + 一号一指纹seed + 一号一proxy，状态持久化
├── persona      # 人设: 地域/兴趣词/活跃时段/浏览偏好
├── store        # 状态库(SQLite): 阶段 / 今日配额 / 风险分 / 互动历史去重
├── behavior     # 行为编排: 阶段FSM + 概率动作序列(浏览/搜索/点赞/收藏/评论)
├── rhythm       # 节奏: 时段曲线 + 日配额 + 动作间最小间隔
├── scheduler    # 调度: 每号一协程，按节奏驱动 behavior
└── riskguard    # 熔断: 读 page_check 的风控信号 → 暂停该号 + 冷却
```

**首要架构改造点**：把 `service.go` "每动作开关浏览器" 改成 **"一号一常驻浏览器会话"**（一个账号一次养号会话内复用同一个 `*rod.Page` / `Browser`），否则养号节奏、上下文、成本都不成立。
